# Interactive CLI menu Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `afkadb` with no arguments opens a menu that runs any mode and edits every setting, so the daily operations of this fork stop requiring memorised command names and a text editor.

**Architecture:** A new `adb_auto_player/cli/menu/` package of pure functions plus one thin loop. Everything that decides - which fields a model exposes, how a typed value is parsed, what a screen contains, what bytes get written - is a function taking data and returning data, with no `input()` and no `print()` inside it. The loop is the only code that touches the terminal, and it takes its input callable as an argument so tests supply a list instead of a pty. Same split as `services/solstice/` versus its mixin.

**Tech Stack:** Python 3.13, Pydantic v2, `tomllib` to read, `tomli-w` to write, pytest.

## The five things that will break this if ignored

### 1. Writing through the model DELETES settings

`TomlSettings.from_toml` validates with `extra="ignore"` (`models/pydantic/toml_settings.py:32-34`). `App.toml` carries `notifications_enabled` (line 10) and `action_log_limit` (line 14); **neither exists in `app_settings.py`**. Dumping a model back to TOML therefore drops them.

**The editor never serialises a model.** It loads the raw dict with `tomllib`, replaces exactly the keys the user changed, and writes that dict back. The model is used to VALIDATE and to describe fields, never as the source of what gets written. **[v1 was wrong: it planned a model round-trip and an identity test that would have "passed" while deleting two live settings.]**

### 2. `from_toml` swallows validation errors

It catches and falls back to defaults (`toml_settings.py:38-41`), so "it loaded" proves nothing. Validation before a write must call `model_validate` DIRECTLY and let `ValidationError` propagate to the caller, which reports it and writes nothing. **[v1 was wrong: it assumed loading implied validity.]**

### 3. The wrapper never passes an empty argv, and demands an emulator

`~/Dev/afk-bot.sh` (in `todor-wdb/the-drey-setup`) does two things that make the menu unreachable:

- `"${@:---help}"` turns no arguments into `--help`, so the CLI never sees an empty argv.
- It exits early unless `sys.boot_completed` is 1, so no emulator means no menu - even though editing settings needs no device at all.

Both must change, in that repo, as part of this work. The emulator check moves to the paths that actually need a device: a mode runs, settings do not.

### 4. Not every field is a scalar

`excluded_heroes: list[HeroesEnum]` (`games/afk_journey/settings.py:60`), `squads` and `towers: list[TowerEnum]` (lines 115, 142), plus the custom-routine task lists. A scalar-only editor cannot represent these.

Scope: **lists of enums are editable as a multi-select** (numbered, toggle by entering a number, blank line to finish). Task lists and anything else non-scalar are **displayed read-only with a line saying to use the GUI**, rather than silently omitted. A setting the editor hides is a setting the operator thinks they have changed. **[v1 was wrong: it planned scalars only and did not say what happens to the rest.]**

### 5. `App.toml` is not read from the profile dir

`util/execute.py:80-82` reads it from the root config dir, with a comment saying exactly that. The editor resolves the same path the same way rather than assuming `--app-config-dir` is where every file lives.

## Task 1: entry points

- [ ] `afkadb help` prints exactly what no-arguments prints today, exits 0.
- [ ] Empty argv **and** `sys.stdin.isatty()` opens the menu.
- [ ] Empty argv and NOT a tty prints the listing to stderr and exits non-zero - a script that lost its argument must fail loudly, never block on a prompt nobody can answer.
- [ ] `SettingsLoader.set_app_config_dir` / `set_resource_dir` run BEFORE the menu branch. `get_app_config_dir` raises `RuntimeError("App Config Dir undefined")` (`settings_loader.py:25-30`) otherwise.
- [ ] Assert at build time that no game command is named `help`. (Verified absent today; assert so it stays that way.)

Tests: the three argv paths with `isatty` patched; a test that the menu branch is not reached before settings init.

## Task 2: schema-driven field enumeration

- [ ] `fields_of(model)` walks `model_json_schema()` and yields, per leaf: TOML alias, title, description, type, constraints, current value, and a `kind` of `scalar | enum | enum_list | unsupported`.
- [ ] Resolves `$ref` into `$defs` - nested models and enums are refs, not inline. A walker that does not follow refs sees nothing.
- [ ] Nested models become nested sections, matching the TOML's shape.
- [ ] Missing `title` falls back to the alias, never to an empty label.

Tests: against `AFKJourneySettings`, assert every key present in `AFKJourney.toml` is enumerated; assert `auto_bet_threshold` reports **`ge=50, le=95`** (`settings.py:209-212`) **[v1 was wrong: it claimed 0-100]**; assert `excluded_heroes` is `enum_list` with `HeroesEnum`'s members as choices.

## Task 3: parsing and validation

- [ ] `parse_value(raw, field)` handles bool (`y/n/true/false`), int, float, str, enum-by-number, and enum-list toggling.
- [ ] Returns an error rather than raising, for out-of-range and unparseable input.
- [ ] An empty line means "leave unchanged".

Tests: table-driven over every kind including rejections and the empty line.

## Task 4: the save path

- [ ] `save(raw_dict, changes, model_cls, path)`:
      1. apply `changes` to the raw dict loaded by `tomllib`,
      2. `model_cls.model_validate(...)` and let a `ValidationError` abort,
      3. write with `tomli-w` to a temp file in the same directory, `os.replace` it.
- [ ] A validation failure writes NOTHING.
- [ ] **Unknown-key preservation test:** load `App.toml`, save with one unrelated change, assert `notifications_enabled` and `action_log_limit` are still present and unchanged. This is the test that would have caught the v1 design.
- [ ] Round-trip test on `AFKJourney.toml` asserting the parsed dict is unchanged when nothing is edited. Note this is a RAW-DICT comparison, not a model comparison - the legacy string-form custom routines normalise to objects through the model, so a model-level identity test cannot pass.

## Task 5: the loop

- [ ] Top menu: Run a mode / Game Settings / App settings / Quit.
- [ ] "Run a mode" lists commands grouped as `help` does, numbered, and executes via `resolve_command` then `find_command_and_execute`.
- [ ] Settings screens list sections, then fields, showing current value and description.
- [ ] Ctrl-C and EOF exit cleanly at any depth, no traceback, no partial write.

Tests: drive the loop with a scripted input list; assert the calls made and the bytes written.

## Out of scope

- No TUI framework, no mouse, no colour beyond the existing log handler.
- No profile switching - there are no profiles in the CLI.
- No editing of `data/` or anything outside the three TOMLs.
- Task lists and other non-scalar settings are shown read-only, not edited.
